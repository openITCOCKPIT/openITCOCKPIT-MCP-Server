# Evals

Two measurements, for two different questions, and the records of what we
measured with them.

Everything here is meant to be run by anyone, not only by us: the dataset is
generated by a script in this repository, so a number in a baseline below can be
reproduced rather than taken on trust.

## Can a model do the job? (`oitc-mcp-eval`)

The runner ships with the server and is documented in
[docs/evals.md](../docs/evals.md). It asks operator questions against a live
instance and checks whether the answers carry what the tools returned.

The cases in this folder are written for the scale test dataset, so they name
hosts such as `scale-srv-339` and expect the counts that dataset produces. Build
it first, against an instance you are willing to fill with 500 hosts:

```bash
python scripts/seed_scale_dataset.py
```

Then point the eval at that instance and at an OpenAI-compatible model endpoint:

```bash
export OITC_BASEURL=https://your-instance OITC_APIKEY=...      # the instance
export OITC_EVAL_BASE_URL=https://your-endpoint/v1             # the model
export OITC_EVAL_API_KEY=...

oitc-mcp-eval --model <your model> --samples 5 \
  --toolsets health --system-prompt en/general --system-prompt en/health \
  --cases evals/agent_cases.toml --results evals/results
```

| file | what it covers |
|---|---|
| `agent_cases.toml` | reading: overview, search, health, noise, notifications, handover, investigation |
| `agent_write_cases.toml` | acting: acknowledge, downtimes, check now, impact, configuration export (`--write --toolsets operations`) |
| `agent_lifecycle_cases.toml` | taking objects out of the monitoring and deleting them (`--write --toolsets lifecycle`) |
| `agent_config_cases.toml` | changing configuration through `update_*` (`--write --toolsets config`) |

The files that act set the instance up and clean up after themselves, and run
one case at a time. Run them against a throwaway instance;
`scripts/eval-throwaway.sh` creates and removes one for you.

## Does a model pick the right tool at all? (`run.py`)

A cheaper measurement that needs no openITCOCKPIT at all: one question, one
answer, and the first tool call is scored against the tool the question calls
for. It reads the tool schemas from the server in-process, so it is the quick
way to see what a change to a description does.

```bash
python evals/run.py --model <your model> --samples 5
```

`cases.toml` holds one expectation per question. `tools = []` means no tool
covers that task yet, which a run reports rather than counts as a miss.

## The two models in the baselines

Our own runs compare a large reference model with a small one. The endpoint ids
are ours; the labels are what the baselines use.

```bash
MODEL_A=h200-heavy-think-01-01      # DeepSeek V4 Flash, the reference
MODEL_B=h200-light-no-think-02-02   # Qwen 3.6 35B-A3B, the small one
```

## Results

`results/` holds raw records and is not committed. Every run is also kept in
SQLite under whatever `--results` points at, so runs stay comparable;
`oitc-mcp-eval --history`, `--compare`, `--by-tool` and `--by-toolset` read it
back. `baselines/` holds the summaries worth keeping, each saying what was
measured and what it changed.

## These questions are a test set

They are published so the measurement can be reproduced and argued with. That
only works while models have not memorised the answers.

**Do not include this folder in training data.** If you scrape repositories for
training corpora, exclude it. The cases that ship with the server
(`src/openitcockpit_mcp/evaluation/cases/`) are written differently on purpose:
they hold an answer against what the tools returned in the same conversation, so
they keep working even for a model that has read them.
